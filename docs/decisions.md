**Date:** 2026-05-12
**Decision:** Lock Phase A item 2 schema with pgEnum for all enums, ABO/Rh values for `blood_type`, and `restrict` (not cascade) for required cross-entity FKs in clinical history
**Context:** Phase A item 2 (schema) had three tactical decisions not prescribed by design.md Phase 4 / 9.2: (1) how to implement enum columns, (2) what values to use for `blood_type` (Phase 4 says "enum" but doesn't enumerate), (3) `onDelete` policy on required FKs other than `patient_id` (where Phase 9.2 mandates cascade).
**Choice:** (1) Native Postgres `pgEnum` — true ENUM types, one declaration per enum, snake_case names. (2) `blood_type` values: standard ABO/Rh set (`A+ | A- | B+ | B- | AB+ | AB- | O+ | O-`). (3) Required cross-entity FKs in clinical records default to `onDelete: "restrict"`. In v1 only `visits.doctor_id` qualifies; pattern applies forward. Cascade reserved for `patient_id` (Phase 9.2 mandate) and parent-child pairs where the child has no independent meaning (change logs, `lab_results→lab_reports`, `symptom_episodes→symptom_types`, `extraction_sessions→reports`).
**Alternatives considered:** (1) `text` + CHECK constraint — easier to add/remove values via simple ALTER TABLE, but no automatic Drizzle TS union, more boilerplate. Rejected because pgEnum is cleaner and the cost of adding values later (`ALTER TYPE … ADD VALUE`) is acceptable. (2) Inline ABO/Rh values vs. broader set with "unknown" — went with the standard 8 since Phase 4 isn't prescriptive and ABO/Rh is the universal clinical set. (3) `cascade` on `visits.doctor_id` — rejected during /check review: a doctor row deletion would silently nuke a patient's entire visit history. UI should guide merge/reassign instead.
**Reasoning:** pgEnum aligns with Drizzle's recommended pattern for typed enums and gives free TS unions via `$inferSelect`. The ABO/Rh choice will appear in the patient form's blood-type dropdown — call out at UI build time if the patient population needs a broader set (e.g. include "unknown" or "Rh null"). The restrict-by-default FK policy is now a project-wide rule saved to memory (`feedback-fk-delete-behavior`); apply forward to any new required cross-entity FK.

**Date:** 2026-05-12
**Decision:** `updated_at` columns auto-update at the Drizzle ORM level (`$onUpdate(() => new Date())`), not via a database trigger
**Context:** Every table in the schema has `created_at` and `updated_at` columns per Phase 4 convention (line 219: "assume present on every table"). Postgres does not auto-update timestamps on UPDATE — the mechanism has to come from somewhere.
**Choice:** Drizzle's `.$onUpdate(() => new Date())` modifier. All `updated_at` columns get this treatment in every schema file.
**Alternatives considered:** Database trigger (PL/pgSQL function set in the migration). Rejected: more migration noise, harder to reason about test fixtures, and v1 has no use case where rows are updated outside Drizzle (no direct psql writes, no RLS, no other ORM).
**Reasoning:** App-level auto-update keeps the schema migration clean and matches Drizzle docs. Trade-off (worth knowing): direct SQL writes via psql, Drizzle Studio raw queries, or any future non-Drizzle client will NOT touch `updated_at`. Revisit in v1.5 if real auth + RLS + direct-from-Supabase reads land — at that point a trigger is the safer bet.

**Date:** 2026-05-12
**Decision:** Phase A query helpers ship a minimal first cut — `forPatient(patientId)` per entity plus `active(patientId)` only for medications + conditions; exported as per-entity namespace objects; change-log and specialized helpers deferred until a UI surface needs them
**Context:** Phase A item 6. Phase 9.2:2313-2322 prescribes `db/queries/` with per-entity helpers taking `patientId` as an explicit param (RLS-ready); gives `medications.ts (forPatient, active, ...)` as the only concrete example. Open questions: how broad should the first cut be (the indexing strategy at 9.2:2297-2306 implies several access patterns), and how should the helpers be exported?
**Choice:** 14 files in `db/queries/` mirroring `db/schema/` — singular file naming, matching the existing schema convention (design doc 9.2:2316-2319 example uses plural; doc is internally inconsistent with its own singular schema list). Each file exports a typed namespace object (`patientQueries`, `medicationQueries`, …) so the barrel `db/queries/index.ts` is collision-free even when multiple entities have a same-named helper (`active()` on both medications and conditions). Coverage shipped: `forPatient(patientId)` on every entity (or `getById` for the patient root, `getForPatient` for the lifestyle singleton, `forReport`/`forPatient` paired for lab + symptom child entities), plus `active(patientId)` for medications and conditions (the two cases the design doc explicitly cites). Helpers are async, return resolved row arrays from `db.select().from(...).where(eq(..., patientId))` SQL-style queries.
**Alternatives considered:** (a) build the full set the indexing strategy implies (recent-by-type for vitals, date-windowed for episodes, change-log `forParent(parentId)`, child-by-parent for `lab_results.lab_report_id`) — rejected per CLAUDE.md "don't pre-build for hypothetical requirements"; add when the first caller lands. (b) flat per-file function exports (`listMedicationsForPatient`) — rejected, less ergonomic at call sites and risks barrel collisions. (c) Drizzle relational query API (`db.query.medications.findMany(...)`) — rejected; SQL-style is more explicit about which columns and joins are involved, and matches most Drizzle examples in circulation.
**Reasoning:** Query helpers exist to compress the common patient-scoped read at call sites AND to be the seam for v1.5 RLS — taking `patientId` as an explicit parameter today means flipping on RLS later doesn't change any signatures. Building only what callers actually need (and what the design doc cites by name) keeps the surface honest. The namespace-object export style gives autocomplete and a stable barrel as new helpers get added. Change-log and specialized helpers get added when their UI surface lands in Phase D (medication/condition detail pages).

**Date:** 2026-05-13
**Decision:** Phase B shared-infra design: deterministic vault-context output, slug-based citation format, single UUID→slug index threaded to all serializers, insight framing modes, brief-exclusion as v1.5 forward-compat no-op
**Context:** Phase B items 1-4 ship the foundation every agent depends on (`lib/agents/_shared/{vault-context,errors,schemas,serializers/}`). Multiple design calls needed alignment before code lands — determinism contract for prompt caching, citation format alignment between Phase 5.3's outdated XML tag and Phase 10.3's markdown pills, insight framing distinct from Phase 5.6's anti-echo-chamber rule, slug derivation rules, and the brief-exclusion tripwire on a v1 entity that doesn't exist yet.
**Choice:** (1) `buildVaultContext` takes a third `now: Date = new Date()` parameter; same vault state + same `now` produces byte-identical output. Determinism is **per-request**, not across time — values like patient age update on subsequent runs but every call within a single agent invocation is consistent. No `new Date()` / `Date.now()` / `Math.random()` in the serializer + vault-context layer. Re-sort inside the serializer with `id` ASC tiebreaker. Omit empty sections entirely (no `# Allergies\n(none)`). Omit `createdAt` / `updatedAt` from output. (2) Citations use `§ entity-type:slug` markdown pill format per CLAUDE.md and 10.3:3102. The Phase 5.3 XML-tag example is stale; ignored. (3) Each serializer file exports `serializeXxx` + `xxxSlug`. `vault-context.ts` builds a single `Map<UUID, "entity-type:slug">` index once after loading entities and threads it into every serializer that emits cross-entity refs. Slug collisions get `-2`, `-3` suffixes in stable id-ASC order; semantic disambiguation (e.g. `med:amlodipine-5mg`) deferred to v1.5. (4) `serializeInsights` takes a mode parameter (`"deduplication-only"` vs `"full"`) and emits different framing preambles — the anti-echo-chamber rule from 5.6:889-895 is enforced at the vault-context layer, not buried in agent prompts. (5) `excludeBriefs` defaults true; v1 has no Brief entity, so the flag has no v1 data path. Comment marks the future entry point.
**Alternatives considered:** (a) Use UUIDs in citation pills directly (e.g. `§ med:8f3a2b1c-...`) — rejected, ugly AI output and breaks the readable-pill contract. (b) Build the slug index lazily inside each serializer — rejected, duplicates the loop and breaks single-source-of-truth for dedup suffixes. (c) Live with non-determinism (`updated_at` in output, no `id` tiebreaker) and accept cache misses — rejected, prompt caching is the v1 cost-optimization story for synthesis. (d) Inline the insight framing strings in agent prompts — rejected, vault-context is the load-bearing place to enforce framing because the same insight rows can be loaded by either synthesis or insight-gen with different framing needs.
**Reasoning:** The vault-context module is touched by every agent, so the constraints we lock here propagate everywhere. Determinism is a downstream investment: prompt caching only pays off when the cached prefix actually matches. Slug-based citations preserve readable AI output and let the citation parser (Phase C work in `components/ai-message.tsx`) resolve slug → entity at render time. The two-export-per-serializer pattern (function + slug) means serializers are pure and the slug index lives at the orchestrator layer where dedup can be centralized. Brief exclusion as a v1.5 tripwire is cheap insurance — when Brief becomes an entity we want the architectural guarantee already in place, not bolted on. Note: `server-only` was originally specified for `vault-context.ts` but dropped to enable tsx-based smoke tests; the credential boundary is at `@/db` / `@/lib/env` and `postgres-js` makes the dependency graph unbundleable for the client regardless. Documented inline in the file.

(2) **Typo-recovery via reactive delete is queued for a later release**, not shipped. The hypothesis: most "I typed wrong" recoveries happen after the fact, not at entry time. Reactive delete on individual history rows is cleaner than a "this is a correction" toggle. (3) **Clickable clinical cards (Current section → opens log-change dialog with field preselected) queued for a later release.** The user accepted the muted hint below the dose card as sufficient for v1. (4) **Resume from paused → active stays v1.5.** PATCH route comment already locks this; reaffirmed in this session as out-of-scope. Real workflow case noted (parent had a procedure, was paused, now back on) — surfaces in v1.5 alongside the broader status state-machine work. Cap each process at 3. Production (Vercel serverless) is short-lived per invocation so 3 is fine there too. Long-term fix is to move DATABASE_URL to the transaction pooler (port 6543); short-term cap is documented inline. (6) **History sort tiebreaker: `desc(changedAt), desc(createdAt)`.** Date-only form input coerces to noon UTC, so multiple rows logged the same day tie on `changedAt`; without a secondary sort, same-day entries land in arbitrary order. `createdAt` (defaultNow()) captures real insert order and tiebreaks deterministically. Applied to both `forPatient` and `forMedication`. (7) **`changedAt` coerced to noon UTC**, not noon-in-patient-tz. For a Pune patient this lands at 5:30 PM IST on the chosen calendar day — still safe from day-boundary flips, no new datetime helper. A precise `noonInTimezone(dateStr, tz)` sibling of `todayInTimezone` is queued for the next time we revisit `lib/datetime.ts`. Discontinued meds collapse both pieces and the header omits the actions cluster entirely (also resolves /check E2 — no empty-row vertical-space bug). (9) **`MedicationDomainError.kind` extended** with three new kinds: `medication_discontinued`, `invalid_status_transition`, `linked_entity_invalid`. Each maps to a specific HTTP code + voice-compliant message + structured `details` payload (per-field `fieldErrors` for the linked-entity case). (b) **Preventive correction toggle inside the log-change dialog** ("this is a correction, not a change") — rejected; adds cognitive load to every interaction; most typo discoveries happen after the fact. Reactive delete is the simpler mental model and gets queued instead. (c) **Click-on-clinical-card opens dialog with field preselected** as part of item 5 — rejected for this release; the muted hint below the dose card is sufficient signal; clickable cards is a UX upgrade not a bug fix. Queued. (d) **Ship Pause as a separate `…` menu item alongside Discontinue** — rejected; the dialog's field=Status branch already handles active→paused cleanly and exposes the reason+linkedVisit metadata that a menu-button-then-confirmation flow would not. Helper is queued for the next genuinely awkward datetime case. The hard-coded `select-form` / `select-category` variants will be generalized when the first Phase D entity (Condition) needs an inline Select. (i) **Defer the test-scenarios doc** until Playwright suite lands — rejected; manual paging + driving-agent use cases benefit immediately, and writing scenarios while the feature is fresh in memory surfaces spec-vs-impl gaps that would be invisible later. Spawned `.claude/commands/test-scenarios.md` to systematize the pattern for Phase D / future items.
